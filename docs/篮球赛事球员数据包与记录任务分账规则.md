# 篮球赛事球员数据统一平台协作与裁判核验规则

> 状态：已确认产品基线，替代原“主办方安排专职记录员”方案
> 适用范围：赛小蜂篮球 PC 赛事中心、微信小程序、平台统一服务号、现场中控台
> 更新日期：2026-08-19

## 一、核心定位

PC 端、小程序、服务号和球队数据页面属于同一套赛小蜂篮球平台，不建设彼此割裂的数据系统。所谓三方或四方协作，是同一场比赛中的角色与任务分工：

- 赛事主办方在 PC 端创建赛事、场次并分配主裁判；
- 主裁判在小程序接管官方比分板、比赛时间和 MC 控制；
- 原“球员数据统计员任务”按主队、客队拆成两份，分别交由双方主教练负责；
- 每队主教练可亲自记录，也可按技能、按球员或混合方式分发给最多 5 名助理教练；
- 双方教练团队在同一平台内记录本队球员数据；
- 主裁判在同一平台的中控台完成赛后核验；
- 核验通过的数据进入平台统一数据库，并按球队权限展示在对应球队数据视图中。

主办方、裁判和双方主教练形成四方协作；如果只从任务发起、官方执裁、球队记录三个职能看，也可称为三方协作。两种说法不代表存在多个平台。

## 二、调整原因

球员数据的核心使用者是球队教练和家长。裁判或主办方专职记录员通常不熟悉各队球员，容易发生号码、姓名和得分归属错误；裁判同时承担球员统计还会分散对官方比分和比赛秩序的注意力。

因此，平台保留“球员数据统计任务”，但改变任务承接人：由双方主教练分别承接本队任务。教练可自主选择是否记录；不记录不影响球队参赛、官方比分、赛果、积分或晋级。

## 三、统一平台联动流程

```text
主办方在 PC 创建场次并确定主裁判
→ 主队、客队分别递交首发与替补名单
→ 现场数据管理员确认主裁判与两队名单三项完成
→ 数据管理员一键启动本场现场系统
→ 裁判只核对球队、时间和场地后进入比分/时间/MC 控制台
→ 双方主教练进入各自页面并完成助教权限分配
→ 主教练通过服务号通知、邀请链接或二维码发送权限
→ 助教绑定后进入本人操作页
→ 比赛中裁判维护官方比分，教练记录本队球员数据
→ 比赛结束后教练分别提交
→ 平台先做自动一致性和异常检查
→ 主裁判在中控台确认、退回修改或拒绝数据请求
→ 通过的数据进入统一数据库并发布到对应球队数据视图
→ 主办方 PC 获得权限范围内的查询和审计能力
```

服务号负责助教邀请、身份绑定、任务接受和消息通知；小程序负责现场比分控制、球队数据录入和裁判核验；PC 负责场次、主裁判、名单状态、现场系统启动、状态查询和审计。数据管理员不介入球队内部助教分工，主裁判也不配置名单、助教或统计口径。

## 四、角色和权限

| 角色 | 主要职责 | 权限边界 |
|---|---|---|
| 赛事主办方 | 创建赛事和场次、分配裁判、查看任务与核验状态 | 可调用权限范围内的数据，但不能修改教练原始记录或直接将其作为官方 MVP 依据 |
| 现场数据管理员 | 确认主裁判与两队名单完成，一键启动现场系统 | 不配置裁判细项，不介入球队内部助教权限或数据口径 |
| 主裁判 | 维护官方比分、比赛时间、比赛状态和 MC；赛后核验双方数据 | 不承担逐项球员数据录入，不修改教练原始数据后直接通过 |
| 主队主教练 | 设置主队统计口径、分发任务、监控协作、确认并提交主队汇总 | 只能管理主队，不能修改官方比分或客队数据 |
| 客队主教练 | 设置客队统计口径、分发任务、监控协作、确认并提交客队汇总 | 只能管理客队，不能修改官方比分或主队数据 |
| 助理教练 | 每队最多 5 名，按技能、球员或混合任务协作记录 | 只能操作本人“球员×指标”范围，最终提交责任仍归主教练 |
| 平台管理员 | 系统异常与争议处理、审计支持 | 不得无痕修改任何比赛数据 |

每场每队只设一名“数据提交负责人”，默认是主教练。助理教练可以协作，但最终提交、退回后的再次提交均由负责人确认。

平台不强制球队记录全部技术指标。主教练可以选择少量本场需要的数据；未选择指标显示“未统计”而不是 0。只有主教练选择完整球员得分归属时，球员得分合计才必须与官方比分严格一致。详细分发和完整性规则以 `docs/教练团队球员数据任务分发规则.md` 为准。

主裁判既有计分板、比赛时间、节次、犯规、暂停、球权、交换场地、撤销、结束比赛和 MC 能力保持不变。正式比赛只禁用主裁判端“显示阵容”和球员统计入口；机构内部比赛继续保留。该模式差异不得清除底层阵容数据或历史统计。

## 五、数据分轨但不分平台

### 5.1 官方比赛数据

- 球队总比分；
- 比赛时间、节次和比赛状态；
- 球队犯规、暂停和官方赛果；
- 积分榜、排名和淘汰赛晋级。

官方比赛数据由裁判控制台产生，是赛果与晋级的唯一权威口径。

### 5.2 球队教练录入数据

- 球员得分归属；
- 篮板、助攻、抢断、盖帽、失误、个人犯规；
- 投篮命中/未中等扩展技术统计；
- 阵容、上场和换人记录。

这些数据与官方比赛数据保存在同一平台、同一场次下，但具有独立来源和核验状态：

- `source = coach_recorded`：球队教练录入；
- `verification_status`：草稿、待核验、退回修改、已确认、拒绝发布；
- `team_scope`：仅属于主队或客队数据域；
- `published = true/false`：是否已发布至对应球队数据视图；
- `award_eligible = false`：默认不得用于官方个人奖项自动评选。

## 六、MVP 与官方个人奖项边界

主办方后台可以在权限范围内调用已提交或已确认的球队球员数据，用于赛事运营、复盘、查询和争议处理。但教练是本队利益相关方，裁判的赛后核验也只是合理性确认，不等于官方技术台逐事件认证。

因此：

- 教练录入数据即使经裁判确认，也不能自动作为 MVP、得分王、篮板王、助攻王、最佳阵容等官方奖项的统计依据；
- 所有查看页和导出需标注“球队教练录入、裁判确认发布、不可作为官方奖项自动评选依据”；
- 主办方可以采用裁判评议、教练投票或组委会评审产生 MVP，但不能描述为由教练自录数据自动计算；
- 如果未来需要数据驱动官方奖项，必须单独配置官方统计任务、统一记录标准和赛事级认证流程，不能直接改变本流程的 `award_eligible = false`。

## 七、自动核查机制

平台应先自动检查，再把简明摘要交给主裁判，避免裁判重新做一遍技术统计：

1. 仅当主教练选择“完整球员得分归属”时，本队球员得分合计必须等于本队官方总比分；自选或部分统计只显示已记录范围，不作强一致比较。
2. 检查是否出现整场或绝大多数分数集中记录给单一球员，并显示该球员得分占比。
3. 检查不在本场名单、未上场或已移出阵容的球员是否获得数据。
4. 检查单次得分值、事件节次、事件时间和重复事件是否异常。
5. 检查是否在赛后短时间集中补录大量事件，并提示主裁判关注。
6. 检查提交人是否为该队已授权主教练或提交负责人。
7. 扩展技术统计只做合理区间与逻辑冲突提示，不要求裁判逐项背书。

单一球员高得分不等于作弊。系统只标记异常，主裁判结合现场印象、比分过程和教练说明作出判断。

## 八、裁判中控台核验

比赛结束后，中控台将主队、客队分开显示：

- 官方总比分与该队球员得分合计；
- 得分分布、最高得分球员及单一球员得分占比；
- 未上场有数据、赛后集中补录、重复事件等异常；
- 教练提交时间、修改次数和备注；
- “确认发布”“退回修改”“拒绝数据请求”三个动作。

处理规则：

- **确认发布**：官方比分保持不变，锁定该队当前数据版本，并发布到统一平台内的对应球队数据视图。
- **退回修改**：官方比分保持不变，数据退回该队主教练；修改后重新提交。
- **拒绝数据请求**：官方比分保持不变，该队数据不发布，主裁判必须填写原因。

主客队分别核验、分别发布。一方被退回或拒绝不影响另一方，也不影响官方赛果、积分和晋级。

## 九、各端页面要求

### PC 主办方后台

- 显示每场主队、客队的统计任务负责人和状态；
- 状态包括未接受、已选择不记录、记录中、待核验、退回修改、已确认、拒绝发布；
- 显示官方比分与各队球员得分合计的差异；
- 支持查看核验结果、原因、版本和审计日志；
- 支持按权限只读查询和导出已发布数据；
- 固定显示官方奖项禁用说明。

### 裁判小程序

- 作为官方比分、时间和比赛状态的唯一写入端；
- 比赛结束后显示双方数据核验待办；
- 只展示摘要和异常，不把裁判变成技术统计员；
- 有待核验任务时提醒，但不得阻止官方赛果完成。

### 教练小程序

- 接受本队数据统计任务；
- 选择“记录本队数据”或“本场不记录”；
- 只显示本队阵容和球员操作区；
- 顶部只读同步官方比分、时间、节次和连接状态；
- 实时显示球员得分合计与官方比分差异；
- 支持撤销、更正、离线重试和操作审计；
- 提交后锁定，只有裁判退回时才能继续修改。

### 服务号

- 裁判任务邀请与接受；
- 主教练身份和球队绑定；
- 开赛提醒、教练待提交提醒和裁判待核验提醒；
- 已确认、退回修改和拒绝发布通知。

## 十、异常与争议

- 裁判无法到场：主办方在 PC 重新分配，原场次权限立即失效并留痕。
- 教练不记录或未提交：比赛正常结束，系统记为“本场无球队球员数据”。
- 球员得分合计不一致：只能退回修改或拒绝，不能修改官方比分迁就教练数据。
- 裁判误操作：主办方发起复核申请，不允许直接覆盖；处理后形成新版本。
- 离线比赛：各端保留本地事件序列，联网后按事件 ID 去重，冲突进入人工处理。
- 发布后更正：必须生成新版本并保留旧值、更正原因、申请人和确认人。

## 十一、商业边界

本规则只确认球员数据统计任务的承接人、权限、核验与发布机制。原球员数据包是否收费、如何定价及是否产生任务收益，需要根据新的教练自录模式另行确认；在未形成新商业规则前，不沿用旧的专职记录员容量和分账比例作为开发依据。

## 十二、第一阶段实施顺序

1. PC 赛事创建、赛程、场次和主裁判分配上线。
2. 服务号完成裁判/主教练邀请、身份绑定、任务接受和提醒。
3. 小程序完成裁判接管官方主控台及场次权限机制。
4. 平台自动为每场生成主队、客队两份数据统计任务。
5. 小程序完成教练仅记录本队、选择不记录和赛后提交。
6. 中控台完成自动检查、分队核验、退回和拒绝。
7. 已确认数据进入统一数据库，并按球队权限展示。
8. PC 增加查询、审计、争议处理和只读导出。

## 十三、验收标准

1. 全流程使用同一平台、同一赛事和同一场次数据，不产生独立数据孤岛。
2. 每场自动生成主队、客队两份统计任务，分别分配给双方主教练。
3. 教练只能操作本队，且可明确选择本场不记录。
4. 裁判只维护官方比分并做赛后轻量核验，不承担逐项技术统计。
5. 完整球员得分归属与官方比分不一致时不能确认发布；自选或部分统计必须明确口径，未统计项目不得显示为 0。
6. 单一球员异常集中、未上场有数据和赛后批量补录会被标记。
7. 主客队数据可独立确认、退回或拒绝，互不阻塞。
8. 无论球员数据状态如何，官方赛果、积分和晋级不受影响。
9. 教练自录数据在 PC、小程序、球队视图和导出中均带来源与核验状态。
10. 教练自录数据持续保持 `award_eligible = false`，不得驱动官方 MVP 等个人奖项。
11. 所有提交、修改、核验、拒绝和争议处理均可审计。
